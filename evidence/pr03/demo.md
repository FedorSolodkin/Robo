# Демонстрация: нода patrol

## Роли init, spin, callback, Ctrl+C

- **`rclpy.init()`** — инициализирует клиентскую библиотеку ROS 2 для этого
  процесса (контекст DDS, обработка аргументов `--ros-args`). Без него нельзя
  создать ни одной ноды.
- **Конструктор `PatrolNode`** только регистрирует подписку
  (`/turtle1/pose`), издателя (`cmd_vel`) и таймер (0.1 с) — на этом этапе
  ничего ещё не выполняется, это просто объявление "что нода умеет".
- **`rclpy.spin(node)`** — блокирующий цикл обработки событий: именно он
  вызывает `_on_pose` при приходе сообщения в подписку и `_on_timer` по
  срабатыванию таймера. Без `spin()` колбэки **никогда не вызовутся**, даже
  если подписка и таймер объявлены корректно — объявление и выполнение это
  разные вещи.
- **`Ctrl+C` (SIGINT)** — прерывает `spin()` исключением
  `KeyboardInterrupt`, перехваченным в `main()`; после этого `destroy_node()`
  и `rclpy.shutdown()` освобождают ресурсы. Это останавливает **процесс
  patrol**, но не является командой торможения черепахи — см. ниже.

## Исправный запуск

```bash
ros2 run patrol patrol --ros-args -r cmd_vel:=/turtle1/cmd_vel
```
До первой полученной позы таймер публикует нулевой `Twist` (черепаха
неподвижна — см. `select_command(None) == (0.0, 0.0)`, покрыто тестом).
После прихода первой позы — `linear.x=0.5`, `angular.z=0.3`: черепаха едет
по дуге.

## Разрыв связи (относительный топик)

Без remap командa по умолчанию публикует в `/cmd_vel` (относительно
пространства имён ноды), а не в `/turtle1/cmd_vel`, который реально слушает
`turtlesim`:

```bash
ros2 run patrol patrol
```
`ros2 topic info /cmd_vel --verbose` → Publisher count 1, Subscription
count 0. `ros2 topic info /turtle1/cmd_vel --verbose` в то же время →
Publisher count 0, Subscription count 1. Поза черепахи не меняется
(полный вывод — [demo-run.txt](demo-run.txt)).

## Исправление через remap

```bash
ros2 run patrol patrol --ros-args -r cmd_vel:=/turtle1/cmd_vel
```
`ros2 topic info /turtle1/cmd_vel --verbose` теперь показывает и издателя
(`patrol`), и подписчика (`turtlesim`) на одном топике. Измеренная реальная
частота команды за 10 секунд (`ros2 topic hz /turtle1/cmd_vel`):

```
average rate: 10.000
	min: 0.099s max: 0.101s std dev: 0.00021s window: 79
```
Совпадает с периодом таймера (0.1 с → 10 Гц) с точностью до долей процента.

## После остановки patrol: не мгновенное торможение

Поза сразу после измерения (патруль ещё работает):
```
x: 3.9063, y: 7.5389, theta: -1.7712, linear_velocity: 0.5, angular_velocity: 0.3
```
Отправлен `SIGINT` процессу `patrol`. Поза через ~2 секунды:
```
x: 3.8865, y: 7.0056, theta: -1.4499, linear_velocity: 0.0, angular_velocity: 0.0
```
Координаты **успели измениться** между этими двумя снимками (черепаха
проехала ещё какое-то расстояние по инерции последней полученной команды),
и только затем скорость осела в ноль. Повторное чтение позы ещё через 2
секунды даёт **точно такие же** координаты — движение действительно
прекратилось, а не просто временно отсутствует новое сообщение. Вывод:
исчезновение процесса `patrol` не эквивалентно мгновенной команде
торможения — последствия последней отправленной команды доигрываются, и
нужно дождаться фактической остановки `turtlesim`, а не полагаться на сам
факт завершения процесса.

Полный протокол команд — [demo-run.txt](demo-run.txt). Чистая остановка
`ros2 launch` (та же техника, что в ПР02: `setsid` + `SIGINT` всей группе
процессов) подтверждена записью "clean shutdown after 2s" в конце того же
файла.
