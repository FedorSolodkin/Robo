# Команды ПР02

## Три команды Linux из подготовки терминала

**`mkdir -p src evidence/pr02`** — создаёт сразу оба каталога, включая
недостающие промежуточные, и не падает с ошибкой, если один из них уже
существует (без `-p` вторая попытка создать существующую папку вернула бы
ошибку).

**`printenv ROS_DISTRO ROS_DOMAIN_ID`** — печатает значения перечисленных
переменных окружения текущего терминала. Результат в этом прогоне:
```
lyrical
16
```
Показывает, что среда действительно подключена (`source
/opt/ros/lyrical/setup.bash` сработал) и домен выставлен так, как нужно для
опыта.

**`ros2 pkg prefix turtle_bringup`** — печатает путь, куда собранный пакет
установлен (`/work/install/turtle_bringup`). Это путь `install`, а не путь
исходников в `src` — то есть команда подтверждает, что `colcon build`
реально что-то установил, а не просто прочитал исходники с диска.

### `>` и `|`

`>` перенаправляет стандартный вывод одной команды в файл, **заменяя** его
прежнее содержимое (`команда > файл`). `|` передаёт стандартный вывод одной
команды прямо на стандартный вход следующей, без промежуточного файла
(`команда1 | команда2`). В этой работе оба использовались вместе:
`colcon build ... 2>&1 | tee evidence/pr02/build.txt` — `tee` получает вывод
через `|` и одновременно показывает его на экране и пишет в файл через `>`
внутри себя, `2>&1` перед `|` смешивает поток ошибок с обычным выводом, чтобы
`tee` увидел оба.

### `source` и запуск новой программы

`source файл.sh` выполняет команды сценария **в текущем процессе оболочки**:
переменные окружения (`ROS_DISTRO`, пути `PATH` и т.д.), которые он
экспортирует, остаются доступны после того, как `source` закончил — именно
поэтому `source /opt/ros/lyrical/setup.bash` в начале терминала влияет на
все последующие команды `ros2` в этом же терминале. Запуск новой программы
(`ros2 pkg create ...`, `colcon build ...`) создаёт **отдельный дочерний
процесс**: что бы он ни делал с переменными окружения внутри себя, на
родительский терминал это не повлияет — эти изменения исчезают вместе с
завершением процесса.

Пустой пакет собрался без launch-файла:
```
Starting >>> turtle_bringup
Finished <<< turtle_bringup [3.60s]
Summary: 1 package finished [3.87s]
```
(полный лог — [build-empty.txt](build-empty.txt)). После добавления
`launch/sim.launch.py` и записи в `setup.py` пересборка тоже прошла успешно
([build.txt](build.txt)), и `ros2 pkg prefix turtle_bringup` +
`ls .../share/turtle_bringup/launch` подтвердили, что файл реально
установлен, а не просто лежит в `src`.

## Запуск и остановка launch

```bash
ros2 launch turtle_bringup sim.launch.py
```
Открывается ровно одно окно turtlesim, `ros2 node list` в это время видит
`/turtlesim` (полный лог запуска — [launch-run.txt](launch-run.txt)).
Остановка через `Ctrl+C` (в прогоне — эквивалентный сигнал SIGINT всей группе
процессов сессии) отражена в логе строками:
```
[turtlesim_node-1] [INFO] [...] [rclcpp]: signal_handler(signum=2)
[INFO] [turtlesim_node-1]: process has finished cleanly [pid 52]
```
То есть запущенный launch-ом `turtlesim_node` действительно завершается
вместе с остановкой самого launch, а не остаётся висеть в фоне — подтверждено
и по логу, и отдельной проверкой процессов после остановки
([launch-nodes.txt](launch-nodes.txt): "no launch/turtlesim processes left").

## Связь команды с движением

`ros2 interface show geometry_msgs/msg/Twist` показывает поля сообщения:
`linear` и `angular`, каждое — вектор `x, y, z`. `ros2 topic type
/turtle1/pose` возвращает `turtlesim_msgs/msg/Pose`.

Поза до команды: `x=5.5444, y=5.5444, theta=0.0`. Публикация одной команды
```bash
ros2 topic pub --once /turtle1/cmd_vel geometry_msgs/msg/Twist \
  '{linear: {x: 1.0}, angular: {z: 0.5}}'
```
даёт позу после: `x=6.5093, y=5.7970, theta=0.5040` — черепаха проехала
вперёд с одновременным поворотом, ровно как задают ненулевые `linear.x` и
`angular.z` одновременно (полный вывод —
[movement-commands.txt](movement-commands.txt)). Без повторной публикации
движение не продолжается: `ros2 topic pub --once` шлёт одно сообщение, а не
устанавливает скорость навсегда.

## Разрыв по неправильному имени топика и исправление

Публикация в `/cmd_vel` вместо `/turtle1/cmd_vel` создаёт издателя, у
которого **нет подписчиков** (`ros2 topic info /cmd_vel --verbose`:
Publisher count 1, Subscription count 0), в то время как настоящий топик
`/turtle1/cmd_vel` в этот момент имеет подписчика (`turtlesim`), но **нет
издателей** (Publisher count 0, Subscription count 1) — сообщения физически
некому доставить, хотя тип сообщения (`geometry_msgs/msg/Twist`) правильный
и домен (16) совпадает. Поза черепахи всё это время не меняется.

После исправления имени на `/turtle1/cmd_vel` та же самая команда
воспроизводит то же движение (`x=6.5093, y=5.7970, theta=0.5040` — совпадает
с первым запуском при том же старте, что ожидаемо). Полный вывод сравнения —
[break-fix.txt](break-fix.txt).

**Вывод:** правильного типа сообщения недостаточно для доставки — DDS
сопоставляет издателя и подписчика по имени топика (плюс тип и совместимый
QoS), и несовпадение только имени топика полностью рвёт связь, при этом ни
одна из сторон не сообщает об ошибке напрямую — обнаружить проблему можно
только явно сравнив `ros2 topic info` для обоих имён.
